Cassandra: la clave de partición es la decisión

PRIMARY KEY (
  (partido_id, bloque_horario),
  creado_en, comentario_id
) WITH CLUSTERING ORDER BY (creado_en DESC, ...)

Un partido se reparte en bloques de 5 minutos, así no queda una partición infinita, y leer lo último arranca desde la punta.

No todos los datos necesitan la misma consistencia

Estado del partidoIRISFuerte. %Save() guarda todo o nada; una transición ilegal da 409.
Fichas y grafoMongoDB, Neo4jSe escribe con cuidado; una lectura algo atrasada no daña.
Comentarios y estadísticasCassandra, InfluxDBEventual. Mejor tarde que no poder escribir.
Caché y sesiónRedisTransitorio. La ficha se invalida con DEL; el TTL de 60 s es el tope.

El TTL no da coherencia: es la red de seguridad si la invalidación se pierde. Hasta 60 segundos de marcador viejo sería el peor caso.

Con un nodo no hay partición de red que tolerar: No medido CAP, nodos caídos y regiones. Es una decisión de diseño, no un resultado.

Qué se pierde

Comentarios que el cliente no reintente: la API no guarda pendientes. Sesiones, si se pierde Redis. Muestras, si el productor no reintenta.

Qué decidimos

Servicio degradado: nunca un 200 vacío, y no se saca la API por una sola base. Se recupera sin borrar volúmenes.

  2. ¿La API o el adaptador?
  3. ¿Hay errores? ¿De qué base?
  4. ¿Se saturó el host?

Hito 12: comparacion.md, mismo commit a6609bb, misma notebook (Windows 11, 8 CPU, 15,7 GB)

Lo que no podemos afirmar, y lo que cuesta

No medido

  • Capacidad máxima: atendimos 60 ops/s, no sabemos hasta dónde llega
  • 300 comentarios/s: llegamos a 10,9/s
  • Varios nodos, réplicas y regiones
  • Varios partidos a la vez y red real
  • Una comparación medida contra una base relacional

El costo de seis productos

  • Seis backups, actualizaciones y diagnósticos
  • Más memoria: solo Cassandra usó unos 4,6 GB
  • Conocimiento repartido y monitoreo desparejo
  • Hay datos de partido en Neo4j y en IRIS

Con una carga como la de nuestro laboratorio, una base relacional alcanzaría para comentarios y estadísticas. NoSQL se justifica por los picos proyectados y por seguir escribiendo ante una falla, y eso falta probarlo con varios nodos.

Por qué esta combinación es adecuada

  • Modelos: cada dato usa la estructura que abarata su acceso.
  • Distribución: la partición y las réplicas se decidieron por módulo, según cuánta consistencia necesita.
  • Fallas: separar las bases limita el daño. Lo medimos.
  • Observabilidad: permite saber dónde mirar antes de culpar a una base.
